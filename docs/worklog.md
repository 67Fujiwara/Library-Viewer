## 2026-09-19 サイドバー開閉時に画面が暗くなる問題

- 症状: 左右パネルを開閉するとアニメ中に画面が暗くちらつく
- 原因: `Viewer3D.resize()` が `renderer.setSize()` のあと `requestRender()` で次の rAF に描画を回していた。
  `setSize` は描画バッファを作り直して空にするため、その差のフレームが黒として合成される。
  ResizeObserver は rAF のあと・ペイントの前に走るので、**リサイズしたフレームは必ず黒**になり、
  0.18 秒のアニメ中は毎フレームそれが起きていた
- 計測: アプリより後に登録した ResizeObserver から `gl.readPixels` して確認
  - 修正前 5/5 のリサイズで `[0,0,0]` / 修正後 0/5（背景色 `[227,221,211]` が読める）
- 修正: `resize()` 内で `renderNow()` を呼び、同じフレームで描き切る。
  サイズが変わっていないときは早期 return して無駄な再描画もしない
- `test/panels_test.mjs` に黒フレーム 0 を確認する回帰テストを追加

## 2026-09-19 重い STEP の読み込みを速くする

**先に測ってから決めた。** メッシュ精度を落として速くする案は効かないと分かったので採らなかった。

- 計測 1: 1.4MB / 150 部品の STEP で、精度を変えても時間がほとんど変わらない
  (極粗 4.2 秒 / 粗い 3.4 / 標準 3.7 / 細かい 4.4)。**遅いのはメッシュ化ではなく STEP の解析と B-rep 構築**
- 計測 2: `file://` でも blob URL の Worker が動き、コンパイル済み `WebAssembly.Module` を
  postMessage できる → WASM は 1 回だけコンパイルして全ワーカーで共有できる
- 計測 3: GLB に書いて読み直すと 2ms。**変換結果をキャッシュすれば約 100 倍速くなる**

実装:
- `src/js/04-step.js` をワーカープールに作り替え。`Occt.convert()` の API は変えていない
- `src/js/04b-cache.js` + `00b-idb.js`: 変換結果を自前 GLB にして IndexedDB へ。
  鍵は 名前・サイズ・更新日時・精度。40 件 / 256MB を超えたら古いものから捨てる
- 全件キャッシュに当たったときはオーバーレイも待ちフレームも出さない (266ms → 42ms)
- できた端から画面に出す (`pending` を 250ms 間引いて `addDevices`)

結果 (4 コアの計測環境):
- 1 件 3.9 秒 → 2 回目 38ms (**103 倍**)
- 変換中の描画 **54 fps** (それまでメインスレッドが完全に固まっていた)
- 3 件 8.2 秒 (逐次見積り 11.7 秒)。最初の 1 件は 6.0 秒で表示される

ワーカー本数は **2 本** に決めた。3 本にすると throughput は 1.05 倍にしかならず
(2 本なら 1.42 倍)、「最初の 1 件が出るまで」が遅くなるだけだったため。
素の JS の busy loop は 3 本で 2.96 倍出るので、CPU の割り当てではなく
OCC の B-rep 構築がメモリ帯域・アロケータ律速。

**踏んだバグ**: `addDevices()` の後に `Tree.rerender()` を呼んでいて、行を作り直すたびに
横断バッジが消えていた (browser_test が検出)。フォルダ登録を `addDevices()` の中に入れて解決。

## 2026-09-20 「この部品に寄る」を本当に面積が最大の角度へ

板を真横（薄く見える方向）から見たまま寄ってしまう、という指摘。原因は 3 つあった。

1. **候補の角度が格子だけだった。** phi を 0.22π〜0.78π の 5 段しか振っていないので、
   **水平な板を真上から見る角度（phi≈0）に永久に届かない**。実測で、水平な薄板は
   最大面積の 55% までしか見えない角度が「最良」として選ばれていた
2. **三角形を間引いた分の面積を割り増していなかった。** 標本は 12 点。大きい面が数枚 +
   穴まわりの小さい面が大量、という板では、大きい面を飛ばすと面積を大幅に見誤る
3. **遮蔽の計算に 200ms の打ち切りがあり、候補を「動きの小さい順」に見ていた。**
   部品数の多いアセンブリでは打ち切りに当たり、今の角度の近所しか見ずに終わる

### 直し方（2 段構え）
- 1 段目: 遮蔽を無視して **面積だけ**で広く探す（内積だけなので安い）。候補は
  格子（7×12）+ **面積の大きい法線の向き**（`dominantDirs`）+ 今の角度。
  法線を候補に入れておけば「板の面がまっすぐ正面に来る角度」が必ず候補に入る
- そのあと勝った向きの周りを山登りで詰める（格子の 30° 刻みのままだと面が斜めを向く）
- 2 段目: 上位 10 個だけレイを飛ばして遮蔽を確かめる。時間制限は置かない（候補を絞ったので要らない）
- 面積の標本は 1200 三角形まで拾い、**間引いた分だけ面積を割り増す** (`a * step`)

### 検証
- `faces.step` を追加（水平な薄板・立った薄板・柱）。テストは全方位を 2° 刻みで舐めて
  「取りうる最大の投影面積」を出し、寄ったあとの角度がその何 % かを測る
  - 水平な板: **55% → 100%**（カメラが真上へ）
  - 立った板: **65% → 100%**（カメラが真横へ）
- 既存の「隠れている部品へ回り込む」「見えていれば角度を保つ」も従来どおり緑
- `focusNode` の所要時間 0.4ms（前は最大 200ms の打ち切りに当たっていた）

## 2026-09-24 大きすぎる STEP のエラーを読める形にする

373MB の STEP で `[object WebAssembly.Exception]` としか出ない、という報告。

### 測った
大きい STEP を作って、実際に「ファイルを開く」経路で変換した（標準精度）。

| ファイル | 結果 |
|---|---|
| 1.4 MB | 3.0 秒 |
| 19 MB | **102 秒** |
| 59 MB | **764 秒 = 12.7 分**（成功。6000 ソリッド） |
| 120 MB | **3066 秒 = 51 分**（成功。12000 ソリッド） |
| 373 MB | `WebAssembly.Exception`（報告された PC で） |

**時間はファイルサイズの 2 乗に比例する**（点ごとの指数は n^1.35 → n^1.80 → n^1.95）。
120MB でも落ちずに変換しきるので、先に来るのは「待てない」ほう。
n² なので線形外挿は禁物（373MB は 8 時間の計算。実際はその前にメモリで失敗する）。
**裏を返すと分割がものすごく効く**: 120MB を 20MB × 6 なら直列 11 分 (4.6 倍) /
ワーカー 2 本で 8 分 (6.6 倍)。

**最初 59MB を「タブごと落ちた」と誤診した。** 落ちたのは測定スクリプトのほうで、
ファイルを base64 にして `page.evaluate` に渡していたため 79MB の文字列でページが死んでいた。
`setInputFiles` で実運用と同じ経路に直したら 12.7 分かけて成功した。
**測るときは実運用と同じ経路を通すこと。**

### 原因
STEP は読み込むと何倍にもふくらむ。373MB なら
原本 373MB → ワーカーへのコピー 373MB → WASM ヒープ 373MB → **B-rep で数 GB**。
**この wasm は 32bit なのでアドレス空間が 4GB で頭打ち**なので、B-rep の段階で必ず超える。
OCC の C++ 例外は JS 側に `message` が出てこないため `[object WebAssembly.Exception]` としか見えなかった。

### 直した
- `Occt.explain()` を追加。サイズを添えて「大きすぎる → メモリ超過 → 分けて書き出す」と出す。
  小さいファイルで同じ例外が出たときは「壊れているか対応していない形式」と案内する
- 30MB 以上のファイルは、変換中のオーバーレイに「大きいファイルです（N MB）。時間がかかります」
- ワーカーへ渡すときの `slice()` を、ビュー全体がバッファ全体なら省くようにした
  （その場でもう 1 本コピーができていた。ピークが 1 ファイルぶん減る）
- ダイアログ本文の `word-break: break-all` をやめた（「373 M / B」「S / TEP」と語の途中で折れていた）

### 運用の目安 (ドキュメントに追記)
**20MB 以下が実用的 / それ以上は分単位の待ち / 数百 MB は失敗。**
壁になるのはメモリより先に**時間**。装置まるごとではなくユニット単位で書き出し、
ビューアの「追加」で並べる。待つのは最初の 1 回だけ（変換キャッシュ + 格納した glb が効く）。

## 2026-09-24 Fusion: ユニットごとに分けて書き出す

大きいアセンブリを 1 本の STEP にすると詰む問題への根本対策。

### 運用は増やさない
- Fusion のダイアログに **チェックボックス 1 つ**だけ追加（前回の値を記憶するので、
  大きい装置で一度入れたらそのまま）。ルート直下にボディがある / ユニットが 1 つのときは自動で無効
- 書き出し先は今までと同じ 1 つの装置フォルダ。**`meta.json` の `files` が複数になるだけ**で、
  ライブラリ一覧では 1 件のカードのまま。開くと全ユニットがまとめて読み込まれる
  （`openEntry` はもともと `files` を全部読む作りだったので、ビューア側の流れは変えていない）

### 位置をどう保つか
Fusion の STEP 書き出しは、**Component を渡すと自分の原点に置かれた形**で出る。
つまり分割すると組立位置が失われ、そのまま並べると全部原点に重なる。

- `createSTEPExportOptions` には **Occurrence ではなく Component を渡す**と決めた。
  Occurrence を渡したときに配置が保たれるかは版によって当てにならず、
  「保たれた場合」と「保たれない場合」で二重掛けの危険があるため、曖昧さを消した
- 組立位置は `meta.json` の `placement` に **原点 + 3 軸**（mm）で持つ。
  16 要素の行列にしないのは、行優先・列優先の取り違えを避けるため。
  Fusion 側は `Matrix3D.getAsCoordinateSystem()`、ビューア側は `GLB.place()`
- Fusion API の長さは **cm**、STEP と meta.json は **mm** なので原点だけ 10 倍する
- 位置は **STEP → glb にするときに 1 回だけ焼く**。書き戻した glb は焼き込み済みなので
  2 回目以降は当てない（当てると二重になる）

### 検証
`library_test.mjs` に、分割で格納された想定のエントリ（同じ形の STEP 2 本 + それぞれの placement）を追加。
- 開くと 2 ユニットが 1 件として読み込まれる
- 片方は原点、もう片方は x+1000mm・z 軸まわり 90° の位置に**離れて**置かれる（重ならない）
- 書き戻した glb から開き直しても同じ位置（二重に掛かっていない）
- 削除でユニットごと消える

**Fusion スクリプト自体はこの環境では実行できない**（Fusion が無い）。
API の使い方はドキュメントと実装の両面から曖昧さを消したが、実機での確認は必要。

## 2026-09-24 容量 1/23 と、2 回目以降の差分読み込み

「格納する容量が大規模すぎる」「2 回目以降は差分だけ読んで速くしたい」への対応。
クラウド (Autodesk APS) からの直接読み込みは、file:// では OAuth のリダイレクト先にできず
CORS も通らないため見送り（サーバーを立てる構成に変えるなら可能）。まず容量と速度を片づけた。

### 容量: gzip した glb だけを置く → 1/23
**測ったら glb にしても容量はほとんど減らなかった。** 効くのは gzip。

| | 1.36MB の STEP |
|---|---|
| 素の glb | 1.31MB (**96%**) |
| gzip した glb | 0.12MB (**9%**) |

glb は float32 の座標が並ぶだけなので、形式を変えても減らない。
- 共有フォルダに置くのは `<名前>.glb.gz` **だけ**。STEP のマスターは Fusion のクラウドにある
- Fusion スクリプトが置いた STEP は、初回に誰かが開いて glb にした時点で消す（`dropStep`）
- 設定「共有フォルダに STEP も残す」で残せる（既定オフ）
- 圧縮・展開は `CompressionStream` / `DecompressionStream`（ブラウザ標準）。
  **素の `.glb` も読めるままにした**（前の版で作ったライブラリの下位互換。`library_test` で確認）

**踏んだ罠**: glb の名前を `.glb.gz` に変えたのに `meta.json` を直さないと、
次のスキャンで glb が見つからず毎回変換し直しになる。`syncMeta()` で書き戻す。
Fusion スクリプト側が予告する名前も `.glb.gz` に揃えた。

### 速度: 一覧の差分スキャン + 開いた装置のキャッシュ
- `meta.json` の中身を読むのが一番高い（DirectCloud では実体の取得が走る）。
  更新日時とサイズが前と同じなら読まず、IndexedDB の控え (`cat` ストア) を使う。
  実測: 2 回目は **読み直し 0 件**、1 件だけ書き換えたら **読み直し 1 件**
- 存在確認 (`getFileHandle`) は毎回やる。誰かが glb を足したことは次のスキャンで分かる
- 開いた装置の glb は `ConvCache` (preset `'lib'`) に入れ、2 回目は共有フォルダを読みに行かない
- 状況は `#lib-status` の title に出す（読み直し N 件 / 前回のまま M 件 / ミリ秒）

**踏んだ罠**: 偽ハンドルの `getFile()` が毎回 `new File()` を返していたので
`lastModified` が現在時刻になり、差分もキャッシュも永久に当たらなかった。
書き込んだときだけ進むようにした（`ConvCache` のテストで同じ罠を踏んだのと同根）。

### 1 回目の読み込み: 往復の回数を下限まで減らす + catalog.json で先出し
偽ハンドルの 1 操作に遅延を入れて測ったら、**差分スキャンは 2 回目もほとんど効いていなかった**
（省けるのは `text()` の分だけで往復は変わらない）。遅いのは往復の数と直列であること。

| 1000 装置 | 往復 0ms（同期済み） | 往復 2ms |
|---|---|---|
| 前（直列・1 装置 6 往復） | 1.10 秒 | 14.2 秒 |
| 今（一覧だけで判断・並列 8・1 装置 3 往復） | 走査 0.66 秒 / 一覧 **0.16 秒** | 走査 0.64 秒 / 一覧 **0.11 秒** |
| 再読み込み | 0.25 秒 | 0.36 秒 |

- `walk()` は `entries()` の一覧だけで判断する。`getFileHandle` で `meta.json` や glb を探さない
  （空振りが階層の数だけ積み上がる）。往復 = ディレクトリ数 + 装置数 が全部確かめる方式の下限
- フォルダは 8 本ずつ並列に降りる (`pool`)
- 1 回目は `catalog.json` (schema 2、`meta` 込み) を 1 本読んで一覧を先に出し、裏の走査と違えば差し替える
- IndexedDB の控えは `IDB.batch` で 1 本のトランザクションに（1 件ずつだと 1000 件で 600ms）
- `scan()` は 1 本だけ走らせる（自動読み込みと「開く」が重なると entries に二重に積まれていた）

**測定の罠**: `setTimeout(2ms)` は入れ子で 4ms に丸められるので、直列の 2 回目が 1 回目より遅く出た。

### 検索結果のフィルター (タグ / 名称 …、設定で facet を足す)
右パネルの結果の下にピル型の facet を置いた (`07c-filters.js`)。押すと候補と件数のポップオーバー
(バーの幅いっぱいなので 288px でもはみ出さない)。同じ facet は OR、facet どうしは AND。
どれを出すかは歯車 → 検索 → 検索結果のフィルター (switch の一覧、`lv.searchFilters`)。既定はタグと名称。
